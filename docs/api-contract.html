Fenon API · v1

API contract

What developers write with the Fenon SDK, the API it talks to, and what each model takes and returns. How models are executed is handled separately; Part 3 lists what the runner must produce.

Part 1 · SDK

What users write

from fenon import Fenon

client = Fenon()                                    # reads FENON_API_KEY

result = client.pose.hand(model="fenon/hand-pose-hm", input="clip.mp4", mode="recorded")

for frame in result.frames:                         # typed, parsed from the fetched output
    for hand in frame.hands:
        hand.handedness, hand.pixel_landmarks
result.usage                                        # Usage(unit="frame", quantity=300)
result.save("clip.jsonl")

The SDK always processes the whole video. It never sends input.range and has no preview or confidence option; those are Playground features of the API.

Without blocking

job = client.pose.hand(model="fenon/hand-pose-hm", input="clip.mp4", mode="recorded", wait=False)
job.status        # "preparing_input" → "queued" → "processing_frames" → "writing_results" → "succeeded"
result = job.result()
job.cancel()

Live models (later)

with client.<capability>.connect(model="nvidia/groot-n1.7") as session:
    step = session.step(observation)
    step.action

Live work uses an explicit session (as OpenAI, Dreamscale and Dream Labs do). Names are set when the first live model is added.

Behaviour

  1. Local checks, before any request: the file exists and is readable; its extension is .mp4, .mov or .webm (case-insensitive), which gives the content type; mode is "recorded". Size and type limits are enforced by the API when the upload is reserved (413, 415 → InvalidInputError).
  2. Upload. POST /v1/uploads, then the file is streamed to upload_url, reopened and its size re-checked for each attempt. A 403 from storage (an expired or refused URL) gets one new reservation (new Idempotency-Key); a second refusal raises upload_rejected.
  3. Run. POST /v1/runs with {"model": model, "input": {"video": upload_id}}. There is no up-front model lookup: the run's 202 response names its contract. If the SDK doesn't support that contract ID or major version, it cancels the run (zero usage) and raises UnsupportedModelError. A shipped contract version whose schema_sha256 differs also cancels the run, then raises contract_mismatch; a newer minor version of a supported major is accepted with unknown fields ignored. An unknown model is the API's 404 model_not_found.
  4. Waiting. The SDK polls GET /v1/runs/{id}, waiting Fenon-Poll-After-Ms clamped to 250 ms – 60 s, or without it 2 s growing ×1.5 per poll up to 10 s, until a final status. failed and canceled raise RunFailedError.
  5. Ctrl-C. During a blocking call, once the run exists and isn't known to be final, the SDK sends one POST /v1/runs/{id}/cancel (one attempt, 5 s timeout) and then re-raises KeyboardInterrupt; a second Ctrl-C skips the cancel. A cancelled run has zero usage. A Ctrl-C before the run's 202 arrives can't cancel anything. With wait=False the SDK never cancels on its own.
  6. Output. The annotations output is fetched into memory the first time frames or save() is used (videos are capped at 60 s, so outputs are a few MB): 5 attempts as for uploads; a 403 from storage (an expired or refused URL) refetches the run once for a fresh URL, and a second refusal raises output_rejected; a size other than size_bytes raises output_truncated. frames parses it line by line, can be iterated repeatedly, and raises output_invalid naming the first line that fails the row schema. save(path) writes it to path, overwriting, and returns the Path.

How it's built

Every model runs the same three steps, as in Hugging Face Transformers' pipelines (preprocess → _forward → postprocess). The template lives in the capability's base.py; the middle step is the core services:

client.pose.hand(model="fenon/hand-pose-hm", input="clip.mp4", mode="recorded")
   │
   ├─ 1. prepare   (models/pose/base.py)       local checks → upload → {"video": "upl_…"}
   ├─ 2. run       (_core/runs.py)             create run → contract check → poll → fetch output
   └─ 3. parse     (models/pose/hamer/client.py) result + output → HandPoseResult with typed frames
src/fenon/
  __init__.py  __main__.py  _version.py  py.typed
  _client.py             # Fenon: configuration, logging, core services; attaches client.pose
  _core/                 # core services shared by every model
    http.py              # API client and storage client: auth, retries, hints, idempotency keys
    errors.py            # FenonError and subclasses, API error mapping
    logs.py              # FENON_LOG, redaction
    uploads.py           # upload service
    runs.py              # run service: create, contract check, poll, cancel, fetch output
    usage.py             # Usage
    _generated.py        # shared shapes generated from openapi.yaml
  models/
    pose/
      __init__.py        # Pose (client.pose): hand(); a run's contract → its implementation
      base.py            # base classes for any pose model: the template, video prepare, result and job bases
      hamer/
        client.py        # HaMeR: contract, HandPoseResult, HandPoseJob, parsing
        _generated/      # types and contract constants generated from contracts/fenon.hand_pose.video/1.0.0
  • Dependencies point one way: models imports _core, never the reverse; _client.py imports both. A test enforces it.
  • Adding a model with an existing contract needs no SDK change. A new contract adds a folder next to hamer/; a new capability adds models/<capability>/ and one attribute on Fenon.
  • Package: Python 3.11+ (tested on 3.11–3.14); dependencies httpx2 and pydantic (v2); ships py.typed. Logger fenon, enabled with FENON_LOG=info|debug; it never logs keys, bodies, file paths or storage URLs.

EntitlementIn v1 every key can run every listed model; 403 is reserved.

Idempotency

  • Required on every POST: Idempotency-Key, 1–64 characters from A-Za-z0-9-_. The SDK sends a UUID4 and reuses it across retries of the same call.
  • Scope: API key's project + method + path. Identity: SHA-256 of the body canonicalised with the JSON Canonicalization Scheme (RFC 8785).
  • Replay: same key and same body returns the original status code and body, with Idempotent-Replayed: true. Same key, different body: 409 idempotency_conflict. Same key while the first request is still in progress: 409 idempotency_in_progress, retryable.
  • Retention: at least 24 hours. After that a reused key counts as new.
  • Stored responses: only 2xx responses are stored for replay; any other outcome releases the key. A key in progress holds a 60 s lease. A request without a body (cancel) is identified as the canonical JSON null.
  • Renewing an expired upload is a new logical request with a new key.

Runs

POST/v1/runsStart a model on uploaded input
Request
{
  "model": "fenon/hand-pose-hm",
  "model_version": null,
  "input": { "video": "upl_7k2mq9x4ab3d", "range": { "start_s": 2.0, "end_s": 5.0 } }
}

202   // the run object (below), status "preparing_input"

input must match the contract's input schema, else 422 input_invalid with the field in error.details.field. The upload must be in this project with its bytes received at the reserved size, else 422 upload_not_ready or 422 upload_size_mismatch; the upload does not need to be probed yet. The upload's content type and size are checked against the model's limits (415, 413). An upload the input names that isn't in this project is 422 input_invalid with details.field /input/video; end_s ≤ start_s is 422 input_invalid. Decoding, duration and frame-rate checks happen while the run is preparing_input; a failure there ends the run failed with stage: preparing_input, and so does a range that becomes empty after clipping to the video (input_invalid, zero usage). model_version optionally pins an exact version (the SDK doesn't send it); one that doesn't exist is 404 model_not_found.

GET/v1/runs?limit=&after=This project's runs, newest first

Returns { "data": [run, …], "next_cursor": … }. Used for run history (the website's Runs list).

GET/v1/runs/{id}One run

The run object. While not final, the response carries Fenon-Poll-After-Ms.

POST/v1/runs/{id}/cancelStop a run

Returns the run object. A non-final run becomes canceled; a final run is returned unchanged. A client's wait ending never cancels a run.

Run errors

Retries and timeouts

CallRetried onSchedule
Fenon API callsNetwork errors, 408, 409 idempotency_in_progress, 429, 5xx except 501max_retries retries (default 2, so 3 attempts in total); before retry n (from 0) wait random(0, min(8, 0.5 × 2n)) s
Upload PUT, output downloadNetwork errors, 408, 429, 500, 502, 503, 5045 attempts; waits 1, 2, 4, 8 s
Polling a runA poll that fails with a network error, 408, 429 or 5xx other than 501 after its own retriesUp to 8 such polls in a row, then the last error is raised with .job; any other error is raised at once with .job
  • Retry hints (retry-after-ms, then Retry-After in seconds or as a date, then retry_after_s) replace the computed wait when they are 120 s or less. A longer hint means the call is not retried: the error is raised with retry_after_s set. This matches the OpenAI SDK.
  • Poll interval: Fenon-Poll-After-Ms, clamped by the client to 250 ms – 60 s; without it, 2 s, growing ×1.5 per poll up to 10 s.
  • Timeouts: connect 10 s; read timeout (default 60 s) per API call; upload and download 300 s per attempt.
  • Never retried: 400, 401, 402, 403, 404, 405, 409 idempotency_conflict, 413, 415, 422, 501.

Data the service keeps

A proper database (Postgres) holds, per project: uploads (status, size, media), runs (every field of the run object), usage records (one per final run, written in the same transaction as the final status), and idempotency records (key, body hash, stored response, expiry). Run history (GET /v1/runs) is served from it. Uploaded files and outputs live in R2 with no expiry in v1. Run deadlines count from created_at; the service enforces them. Not built yet: in fenon-api these stores are interfaces.

Runner requirements

Differences between hamer-throughput today (commit d743272) and this contract, for whoever runs the model:

  1. Write a result manifest (video, range, joint order, camera with the focal length used). Today the focal length is computed (backend.py:382) but never written.
  2. Fail with input_unreadable when decoding stops before the last frame of the range. Today decoding stops silently (video.py:56) and the run validates against frames processed.
  3. Detect a variable frame rate and fail with variable_frame_rate. Today timestamps assume a constant rate (video.py:58).
  4. Process only the run's range (the existing start_frame and max_frames options) and report progress in frames.
  5. Remove track_id from the hands written to annotations. It is unique per frame only, but duplicate removal sorts on it (geometry.py:64), so keep it internally until after that step and strip it when writing rows.
  6. Report the status transitions preparing_input → queued → processing_frames → writing_results.
  7. The worker → API reporting interface (status, progress, results) and what moves an upload from pending to probing are owned by the execution team.

Schemas and versioning

  1. Normative files (in this folder): openapi.yaml for the shared API; contracts/fenon.hand_pose.video/1.0.0/input.schema.json, result.schema.json, outputs.schema.json, row.schema.json for the model contract. A succeeded run's result and outputs must validate against their schemas. schema_sha256 is the SHA-256 of those four files, concatenated in that order. A published version's files never change.
  2. SDK types are generated from them (Pydantic v2); only helpers are hand-written. CI fails if regenerating changes anything.
  3. Shared fixtures: the same example requests, responses and output rows are tested by the service and the SDK.
  4. Versions: a contract's minor version may only add optional fields; anything else is a new major. An SDK that doesn't support a model's contract major raises UnsupportedModelError.
